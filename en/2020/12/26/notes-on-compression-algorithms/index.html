Notes on Compression Algorithms

titanxxh2020-12-262026-08-22

Know how to solve every problem that has been solved.

What I cannot create I do not understand.

–Richard P. Feynman

An internal competition at work forced me to learn several compression algorithms within a short time last month. I also implemented some of them, including lz77, deflate, bwt, and bcm. You never know until you practice: the moment you begin writing code, you discover that some things you thought you understood were never truly understood. I also recently watched a series of videos about the late physicist Richard Feynman. One detail left a deep impression. After his death, people found that he had preserved the two sentences above in the upper-left corner of his office blackboard, where they would not be erased accidentally.

From a young age, Feynman’s father taught him that knowing and understanding were two different things. He therefore retained the curiosity to think through every problem.
The two sentences express essentially the same idea: only when you can create something yourself do you truly understand it. Reaching that point requires knowing how every problem was actually solved, not merely remembering a conclusion. The highest level of understanding a concept is being able to teach it to somebody else.

Inspired by that idea, I wrote this article to record my recent exploration of compression algorithms.

First, an excellent survey website about compression is Data Compression Explained. It begins with the simplest algorithms and proceeds all the way to state-of-the-art compression. Its section Compression is an Artificial Intelligence Problem is particularly worth reading.

Second, kanzi-go is an open-source library implementing a remarkable number of compression algorithms. The original version was apparently written in Java; I do not know why the author rewrote the entire thing in Go.
The library’s greatest advantage is that it lets you combine arbitrary front-end transforms with back-end entropy coders and test how different combinations compress your files.

deflate = lz77 + Huffman coding

This is probably the simplest compression algorithm. Many languages include an implementation because it is fast and effective for text. On the data files used in our competition, deflate achieved a compression ratio of roughly 0.37.

The lz77 algorithm is very easy to explain: use the already encoded portion as a “dictionary” for encoding the content that follows.

Take mississippi as an example. Suppose we have already encoded miss. As we continue, we can use a pair (jumpBack, matchLen) to reduce repetition and compress the data. jumpBack tells us how many characters to move backward, while matchLen gives the number of characters to match.

At this point, for example, we could output (3, 3), because moving back three characters lets us match the three-character string iss. We could also output (3, 4), matching the four-character string issi. Notice that the final i of the earlier issi and the first i of the newly matched issi are actually the same character. This overlap is allowed.
The goal of lz77 is to make matchLen as large as possible, so the correct output here is (3, 4).

Very long continuous matches are generally unlikely. We can therefore limit maxMatchLen to 256, requiring one byte, and choose maxJumpBack according to our needs. If maxJumpBack occupies two bytes, the search for the longest match covers at most a range of 2^16 positions.

We then use three bytes to represent one pair. Clearly, replacing a match whose matchLen <= 3 is useless; retaining the original characters takes no more space. Implementations therefore usually search only for matches of length four or greater.

On the other hand, ordinary string matching across a 2^16-position range is very inefficient. We can cache the most recent positions of each four-character hash in a linked list. When searching for the longest match, calculate the current four-character hash and inspect the maintained list directly. This greatly improves search efficiency.

I will not introduce Huffman coding in detail. The basic idea is to count symbol frequencies and assign code lengths in descending order of frequency, ensuring that common symbols receive shorter codes.

All right! At that point, I began writing code because I believed I understood both algorithms. When the first implementation was complete, however, I could not achieve the same compression ratio as Go’s standard-library implementation no matter what I tried. My result was far higher than 0.37.

The principal problem was that when jumpBack, matchLen, and literal values—ordinary characters—were mixed together as input to Huffman coding, matchLen and jumpBack distorted the frequency statistics for literals. Their own frequency distributions also differed from those of literals.

Short matchLen values occur especially often, while longer ones become increasingly rare. Lengths 4, 5, 6, and 7, for example, occur much more often than 8 and 9.

jumpBack, by contrast, appears highly random because the range of 2^16 positions is enormous. Huffman coding offers little advantage for data with nearly uniform symbol frequencies.

I had not read the deflate RFC directly. I found the solutions only by comparing my work against the standard library, debugging and examining how it encoded matchLen and jumpBack, which wasted a great deal of time.

The deflate RFC clearly specifies variable-length encoding for matchLen and jumpBack. The matchLen range 4–258, for example, can be mapped to 0–31. Since lengths 4, 5, 6, and 7 occur most often, they may each occupy one value, such as 0, 1, 2, and 3. Values 8 and 9 can both map to 4, with one extraBit distinguishing between them.

After this kind of predetermined frequency-based encoding, a full eight bits are unnecessary for matchLen in most cases. The much larger jumpBack range is handled similarly: compress it to 0–255 and combine the code with extra bits.

To prevent matchLen and jumpBack from distorting literal frequencies during Huffman coding, we encode them separately. In practice, values 0–255 represent ASCII literals, 256 represents EOF and marks the end of the file, and 257–288 represent matchLen. We then calculate frequencies over the range 0–288.

During decoding, if a symbol falls between 257 and 288, subtract 256, use the resulting value to determine how many extra bits to read and recover the actual matchLen, then read the encoded jumpBack. This reconstructs the pair (jumpBack, matchLen), which allows decoding to continue.

With all of that in place, I finally achieved the same compression ratio as Go’s standard-library implementation.

Deflate has additional tricks for reducing output size. Compression generally proceeds block by block, and every block must begin with its own Huffman-code dictionary, which creates cumulative overhead. Canonical Huffman coding can reduce the size of that dictionary data further.

Arithmetic Coding

Clearly, an ancient compression algorithm such as deflate cannot compete with others on compression ratio, so we need to study more advanced algorithms.

In general, compression algorithms can be divided by principle into transforms and entropy coding. Most compression systems on the market combine several transform stages followed by one entropy stage. The kanzi-go library mentioned above lets you experiment with these combinations.

Lz77 is a transform; dictionaries, BWT, and other methods are also transforms.

Huffman coding, meanwhile, is an entropy-based compression algorithm. Its problem is that it cannot achieve the theoretical optimum of information theory.

Suppose we have a bit stream, streamA, in which the probability of 0 at every position is 0.99, and another, streamB, in which that probability is 0.51. Huffman coding constructs the same dictionary for both.

From the perspective of information theory, streamA clearly contains less information and should be easier to compress. Imagine the extreme case where the probability of 0 is 1. We could achieve an infinite compression ratio because we would need to output only the length.

Arithmetic coding solves this problem elegantly. It maps the input to a subinterval between 0 and 1. For each encoded bit, it narrows the current interval according to the bit’s value and probability. Once every bit has been encoded, a very small interval remains. In fact, any number within that interval can serve as the final encoded result.

Decoding reverses the process and restores the input one bit at a time.

Because arithmetic coding can achieve the theoretically optimal compression ratio, almost every state-of-the-art compressor uses it in the final entropy stage.

State-of-the-Art Compression Algorithms

Arithmetic coding itself is not complicated, but estimating probabilities well is extremely complex. In theory, the more accurately you can use existing content to estimate the probability of what follows, the higher the compression ratio. Dynamically adjusting probabilities also improves online compression.

This is the purpose of modeling. Different input sources require different models; an image, for example, needs a two-dimensional model.

The newest compression algorithms often use more complex modeling methods, including machine-learning models from PAQ8 onward and even mixtures of several modeling approaches. That is another complicated subject, and I did not have enough time to understand every model in PAQ. We ultimately chose the Burrows–Wheeler Transform—another classic example of an idea that is easy to understand but difficult to implement—followed by arithmetic coding with a mixed model considering only order 0, order 1, and whether the previous two characters match. If you are interested, the website above provides some simple introductions.

One final complaint: information about compression is genuinely scarce. Search after search eventually led me to a Russian forum, where experts of every kind publish their code. One cannot help admiring the strength of the Russians’ mathematical foundations.
