[Open Agricola Development Diary] EP 8: Letting the Workshop Agent Write Its Own Cards

titanxxh2026-11-202026-11-25

On November 20 I rebuilt the card Workshop.

I’d wanted a Workshop for a long time. I’d think of a new card during a game of Agricola and want to write down the text and try it at the table that same night. I built the first version early in Open Agricola’s development. As I mentioned in the second diary entry, I’d only sat down to tweak the interface and somehow ended up with a Workshop.

The models back then were less capable, so I kept the job small. I listed the interfaces a card could use in the prompt and added a few finished cards as examples. A player wrote the card text, and the agent followed the examples and kept the whole effect inside that one card. That seemed the least hassle. At least the agent wouldn’t rewrite the game engine while writing a minor improvement.

Both agents start from the same guide

Over the months since, the engine gained plenty of new mechanisms, but the Workshop’s list of interfaces and examples never changed. When I asked an agent in the repository to write a regular card, I’d mostly stopped picking examples for it. In the Workshop I still had to tell it which file to open and which mechanism to use. For the rebuild, I wanted the same card text to work whether I pasted it into my coding session or into the web Workshop.

In the repository, the agent reads the project instructions in AGENTS.md. In the Workshop, it reads a system prompt. Both send it first to docs/CARD_AUTHORING.md, the card authoring guide. In the Workshop I fill in only the name, type, cost and rules. The Workshop passes those to the agent along with the repository revision to read, so the interfaces it finds match the engine that will run the card. Repository instructions · Workshop system prompt

You look things up in the card authoring guide by the words on the card. If the text says “Each time you use this space, you also get …”, there’s a section for exactly that. It shows how to declare the trigger, names a card that already does it, and points to the game test that checks it. “When you play this card” and “once per round” have sections of their own. For why a timing was chosen, the guide links to the module documentation and the original design decision. For the exact arguments, the agent reads an example card’s source. The guide also opens with a Card contract, the rules every card has to follow, such as where to record that a card has been used this round. The last section covers testing: play a turn the way the game tests do and see whether the card actually works. When the engine changes again, I only need to update the guide and the example cards in the repository, and both agents read the new version. Card authoring guide · Game test template

The Workshop’s system prompt also decides when the agent may start writing. It can search and read files first, but before it writes any code it has to report what it found and whether the existing mechanisms are enough. If the text doesn’t say who makes a choice, it asks the author (needs-info). If the engine really lacks a mechanism, it names the gap and stops (needs-platform). Only when the effect fits in one native card file (feasible) does it write the source and tests together. The tests need at least one case where the effect fires and one where it must not.

Why was one extra wood on Fishing so hard?

Before the rebuild, I tried the old Workshop with Woodpile Hook. The card text is one sentence: “Each time you use Fishing, you get 1 additional wood.” A042 Forest Lake Hut already does this in the game. The agent worked out that the card needed to know I’d used Fishing, not just that I’d received resources. But I had left action-space triggers off the list of interfaces Workshop cards could use. The agent didn’t make do with some other trigger. It reported the gap. The original Workshop trial

After the rebuild, I gave the new Workshop the same sentence, and the agent found Forest Lake Hut on its own. It also tested two moves that shouldn’t pay out: me going to the Forest, and an opponent going Fishing. Neither gave me the extra wood. Trial after the rebuild

Who gets to agree to this trade?

For Barter Post I again gave only the card text. Once per round, on my turn, I can offer another player 1 grain for 1 wood, and they can refuse. The agent found D122 Clay Carrier. That card buys clay from the game with food, so nobody has to agree to anything. What the agent could borrow was the way it remembers being used this round. So how does the other player get to answer? For that, it went to a game test that hands a decision over to another player. Clay Carrier · The player-switch test

The cover shows this card’s three-player test table. I’m yellow, and I’ve asked blue to trade wood for my grain. Green sits between us with two wood, but green isn’t the one I asked and doesn’t get a say. If blue accepts, blue takes my grain and gives me a wood, and green’s two wood stay put. If blue declines, nothing changes hands, and I’ve still used my offer for the round.

Can a two-space pasture keep the fifth sheep?

On November 24 I gave the agent five more cards to write. I used a local test tool that runs the same generation process as the web Workshop, and gave gpt-6.1-terra the text, type and cost of each card. One of them, Wide Pasture Gate, is a minor improvement that costs 1 clay. Its text reads:

When you play this card, you may take a Build Fences action, paying the usual wood cost. Each of your pastures of at least two farmyard spaces can hold one additional animal after applying any stable multiplier.

This time I didn’t supply any example cards. In the generation log, the first 29 tool calls are all research. Mini Pasture showed how to offer a fence action when a card is played, but its fences are free, and the Gate has to charge the usual wood, so the agent had to look that up separately. Drinking Trough deals with pasture capacity. The card text wants the extra animal counted after the stable doubles the capacity, but does the engine calculate in that order? The agent went and read the pasture capacity code. Click Next below to follow the files it read, up to its second round of tests.

Then, in the web Workshop’s sandbox, I paid 1 clay to play the Gate and picked six fence segments around two adjacent spaces. I confirmed, and it charged 6 wood.

Next I took all five sheep from the Sheep Market. A plain two-space pasture holds four, but this time the placement panel showed 5/5. I confirmed, and all five stayed.

The old Workshop couldn’t have built this card. It passed results between the card and the engine as JSON. That works for an instruction like “gain 1 wood”. The Gate has to hand the engine a function instead: once the engine has applied stables, check how many spaces this pasture covers and add one if there are at least two. A function doesn’t fit in JSON. So the new Workshop writes cards in the same source format as the regular cards in the repository, and loads the card file together with the engine into an isolated Worker in the author’s browser, with no JSON layer in between. Whenever the engine works out a capacity, it can call the Gate’s rule directly. An independent game test also built a stable in this pasture. Two spaces hold four animals, the stable doubles that to eight, and the Gate makes it nine. Workshop design decision

Of the other four cards, two showed their results right on the board. With Timber Frame Plasterer, I could pay 2 wood in place of 1 clay when renovating my three-room wooden house to clay. When I could afford either payment, the game offered both. I played Reed Delivery Slip in round 10. One reed arrived in round 11 and another in round 13, with nothing in round 12.

The model wrote 28 tests across the five cards, and all of them passed in a Chromium Worker. All 16 independent two-player game tests, written in advance from the card text, passed too.

Afterword

Looking back, the old Workshop was me handing the agent fish. I listed the interfaces it could use and picked the example cards, and all it had to do was copy. The new Workshop hands it a fishing rod, a card authoring guide it can search for whatever it needs. The old saying has it that teaching someone to fish beats giving them a fish. As it happens, the card that stumped the old Workshop was the one about going Fishing.

A rod doesn’t land every fish. During acceptance I set one more card, Legacy Ledger: win this game, and the same account starts its next game with 2 extra food. The agent looked around and found that a card can only read and write the current game. For an account to remember a reward and pay it out at the start of the next game, the platform has to change first. The agent listed 8 pieces of evidence and 3 gaps, and wrote no code at all. In the second diary entry I set a rule for the repository: if a card can’t be finished inside its own file, stop and explain why. The Workshop agent now follows the same rule.

The wish from the opening has half come true. I can write down a card and try it that same night, but only on my own, in my own browser. To play it at a table with friends, the card still has to go through code review like any other card in the repository, get merged, and ship with a game release. The model’s own tests all passed, but they count as evidence, not proof. Hammer Crusher alone took me a year to get right, so I’m not about to put a card written that same evening straight onto someone else’s table.

At the end of the launch post I asked who was up for a game. This time the question is a different one. Is there a card you’ve been carrying around in your head for a while? Write it down in the Workshop and try it
