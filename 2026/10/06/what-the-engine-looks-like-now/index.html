[Open Agricola 开发手记] EP 5：引擎现在长什么样

仙雾2026-10-062026-10-06

现在合一个卡牌的 PR，我连 diff 都不点开。看一眼改动落在哪几个目录，和这次的任务对得上，就合了。半年前可不是这样，那时候 Agent 写完一张牌，我得把它写的每一段都翻一遍，看哪里又重复了、哪里又绕过去了。

中间差的不是我变懒了，是引擎和规矩变了。上一篇讲牌是怎么做完的，这一篇我打算具体讲讲引擎现在长什么样，规矩写在哪，还有目前 human-in-the-loop 的部分还剩下什么。

先看地图

规则引擎全在 shared/ 里，前后端共用同一份。服务端的 GameSession 是唯一能改游戏状态的地方，前端只渲染它算好的结果。

引擎是一棵节点树。一个行动进来，被展开成一棵树，运行时只有五种节点：行动、顺序、并行、互斥分支、和/或。跨玩家执行、可选、强制、等待玩家输入，全是节点上的标记，不另造节点类型。行动里套行动、阶段钩子引出的子流程，压进一个子流程栈。

树的叶子叫 action leaf，整个引擎里只有它能写状态。每个行动是一个事务，成功才提交事件；日志只是从事件派生出来的缓存，规则代码不写日志。

围着这棵树的有四块东西：会话层管回合、收获、计分的阶段推进；行动层定义每个行动和支付的算法，还有 11 个可以挂东西的时点；卡牌层一张牌一个文件；领域层管农场、动物、田地这些实体。

和引擎直接相关的不变量有三条，违反了就算架构 bug：节点树是唯一的状态机，卡牌闭环，后端唯一写入者。

规模：二十多万行产品代码，测试比它还多一半。

一张牌是怎么跑起来的

引擎给每个行动固定了执行顺序，卡牌不能改它。一个行动进引擎后是这样走的：

替换 → 行动前 → 能不能做 → 算费用 → 行动本体 → 行动中 → 紧接行动后 → 行动后

能挂东西的时点一共 11 个：主线上七个，行动本体内部三个，行动之外还有一个随时可做的。卡牌在自己需要的时点挂一段处理逻辑，这就是 listener。listener 只能读，真正写状态的只有行动本体里的 action leaf。主路径只负责派发，不认识任何一张具体的牌。

一张牌挂一个时点的居多，挂三四个的也有。Freshman 要把烤面包改成免费打职业，替换、行动前、能不能做、行动后四处都得挂。

还有一件事图里画不出来：行动后那三个尾随时点，读的不是执行那一刻的状态，是行动触发那一刻的快照。这个机制是 Scales 逼出来的。它的效果是“每放一张改良或职业后，如果场上两种牌数量相同，得 2 食物”，可它的 listener 可能被编译成稍后才执行的节点，中间要是又打出了一张牌，比如 Task Artisan 打出后紧接着一个小改良，等它真正执行时数出来的就不对了。BGA 的结算就是这样：Scales 的卡牌文件里写明，Task Artisan 这类牌要等两张都打完才结算，要么 0 要么 4 食物。Open Agricola 让每次触发按触发那一刻的快照各算各的。读这份快照的不止 Scales：Education Bonus 和 Stallwright 按“第几张职业”发奖励，Job Contract 和 Usufructuary 数职业数量，走的都是同一个 helper。BGA 为了 Beneficiary 连打两张职业的情形，在 Education Bonus 和 Stallwright 里各写了一段认 Beneficiary 的特判；这里一张牌不认识另一张牌。

如果同一时点有好几张牌要触发，引擎不排顺序，交给玩家自己选。

listener 为什么不许改状态

有一回，为了去掉几张牌上手写的触发顺序，引擎在派发前先把每个 listener 跑一遍，偷看它会返回什么，好决定要不要弹选择框。Mud Wallower（每用累积格的第 4 次，得 1 头猪）的 listener 是直接给计数器加一的，偷看一次、执行一次，计数器一次加 2。同一个坑里还有 Reclamation Plow，偷看时读到的是动物安置前的旧状态。两个都是自己打牌时撞见的。

偷看当天就去掉了，但问题不在偷看。listener 本来就会被调用不止一次：预览、判断能不能做、真正执行。它要么能重复调用且没有副作用，要么迟早再出一个 Mud Wallower。所以规矩定成：listener 只读状态、返回流程，改状态交给 leaf。

引擎还留了哪些插口

11 个时点只是卡牌能挂的一类插口。一千张牌为什么大多数不用动引擎，答案在下面这张图里：十二类插口，新卡先在这里面找落点，找不到才算基础设施缺口，才轮到补通用机制。AGENTS.md 里那三个动手前的判断，判断的就是这个。

规矩写在哪儿

每条规矩有三个地方可以放。

放在脑子里，人会忘，换个 Agent 就丢。放进 prompt 里好一些，但总归带有不确定性，并且依赖于模型执行过程中的“良心”。放进 CI 里，改错当场变红，不用谁记得提醒。

项目级别的 Harness 在第二篇里只是一个词，到今天是四层：

  1. 指令层：AGENTS.md、CONTEXT.md、决策记录。动手前先把需求和词汇问清；CONTEXT.md 用 Avoid 标出容易混的叫法。
  2. 架构层：一条命令跑 13 项检查。
  3. 验证层：测试说明先于编码，按风险选最小的测试层，分快慢两档跑。
  4. 上线层：发布、回放、游戏里直接报 bug，线上问题回流成 issue 和新规则。

架构层那 13 项里，两项最要紧。一是卡牌特判不进主路径，从三个方向守：effect 文件和行动 id 走白名单；主路径不碰卡牌注册表；卡牌文件引用别的卡牌编号，直接红。二是 listener 不直接改状态。

门禁的一项项都是被逼出来的。有一次 29 张卡被放错了数组，于是有了卡牌归类检查；卡牌边界检查一开始只告警不拦，三个月后才并进必过的清单。

把反复提醒 Agent 的规则，变成项目里会执行的铁律。这是这大半年里最值钱的一句话。

人还要做什么

先说不再由人做的。代码不再逐行看：已合并的 PR 有 382 个，从创建到合并的中位数是 0.66 小时。代码审查交给了模型的交叉 review；写代码的 Agent 逐条回复修在了哪个提交。实现、测试、重构、部署，都是 Agent 做的。

人还在做的：

  1. 定规则。规则书、与 BGA 的实际行为的差异、Open Agricola 自己的架构选择。这些很大程度上依赖玩家经验，和代码品味。
  2. 定架构。这张牌是局部修、复用现有钩子，还是先补通用机制。上一篇里 Hammer Crusher 先补回滚机制再回来做牌，这个决定是人下的。
  3. 看 PR，但大部分不检查。扫一眼目录：一个卡牌任务该动的是卡牌目录、测试和文档，碰了主路径那几个文件，才停下来问为什么。
  4. 实际玩来看 bug。这个其实不考虑 token 消耗的话，可以让 Agent 做。
  5. 把第二次出现的错误写进 Harness。Mud Wallower 之后，listener 不许改状态成了规矩；上一篇里 Stable Manure 那次之后，直接碰田地变成了门禁。

这五件事，我不觉得会永远留在人手里。模型再强一些，2 到 5 可能都可以交出去。

写在后面

《农场主》里我一直最在意 行动效率：前面铺的东西，后面每一轮都在生利息。做这个项目大半年，最大的利息不是一千张牌，是那整个引擎架构，以及项目的 Harness 框架的搭建，才让扩展的接入变得顺畅而无痛。
