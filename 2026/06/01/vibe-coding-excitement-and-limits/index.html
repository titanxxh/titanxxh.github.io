[Open Agricola 开发手记] EP 2：Vibe Coding 上头记

仙雾2026-06-012026-10-05

刚开始做 Open Agricola 的这段时间，一个想法刚在浏览器里跑起来，就忍不住再试一个。本来只是想调一下界面，调着调着，又想加点信息展示，然后又增加了卡牌工坊，Agent 不在干活我感觉好像亏了一样，一不小心就搞到半夜。

这种感觉很像我高中刚学编程的时候，在机房里坐很久，写完一个算法题马上试下一个，仿佛自己又年轻了一回。

由于从来没搞过前端，在没有 Agent 前很多想法其实很难落地，但是 Vibe Coding 把这部分实现门槛一下子降了下来，很多原来嫌麻烦、懒得从头学的东西，终于可以动手试了。

可项目越往下做，我越发现，做出一个功能的兴奋，和维护整个项目的心情，差别还挺大。

翻越愚昧之巅

上一篇写到，我想自己做一套架构更清楚的农场主，也借这个机会体验一下 Agent 能力是否的确来到了生产力拐点。

一开始我用的都是国内模型，Kimi、GLM、MiniMax 都折腾过。这几个里面，我觉得 GLM 最好，东西做得比较完整，也比较听话。不过后来用上 Opus 4.6，差距还是挺明显的，尤其是改 UI 的时候，GLM 总是容易搞错显示，布局、样式、排版这些，换了 Opus 4.6 以后做出来的效果就好不少，也更能按我的要求改，虽然偶尔还是有点问题，至少更听得懂人话了。

我觉得这类前端的工作应该是训练的时候能用上很多成熟的工程经验，因此表现就很容易提高。

有了前端的优秀经验，对于真正的大头卡牌能力我也开始期待让 AI 能更好地发挥。其间 Skills 也试了不少，比如 Superpowers，让它做一个比较明确的功能，看着还不错，需求先通过 brainstorming 聊清楚，之后基本上可以全托管，挺像那么回事。做成几个卡牌以后，我就开始想，能不能让它自己一直做下去？

我甚至开始打睡觉时间的主意。能不能给 Agent 一个目标，让它自己拆任务、写代码、检查，然后继续下一项？我睡我的，它干它的。毕竟白天要上班，能用来折腾自己项目的时间总是有限。

正是这个尝试，暴露了项目当前的诸多问题，也体现了我对模型能力和 Agent Harness 工程的无知。

跨过绝望之谷

真正开始头疼，是让它不断往里面加卡牌以后。单张拿出来看，基本效果通常都能跑，继续翻代码，就发现类似的东西怎么又写了一份。上一张牌有一套，下一张牌又有一套，还不完全一样。想改一下公共行为，先得把这几份都找出来。

有些东西到底应该放在卡牌里，还是放到公共逻辑里，也越来越说不清楚。这次这样做能跑，下一次就接着照这个写，等我要整理的时候，已经牵扯到别的地方了。本来是想加点新东西，结果先看半天旧代码，弄清楚它们到底是什么关系。

最烦的是，Agent 确实一直在干活，功能也确实在增加，但我一点都没觉得省心。它写完了，我还得看哪些重复了、哪些地方又绕过去了，再让它改。

架构文档其实一开始就有，后面也没少补文档和测试。但同一件事写了好几份，之前为什么这么决定的，又散在不同地方，最后还是得我告诉 Agent 去看哪份、按哪个来。文档是越写越多了，解释的活也没少。

“不要重复实现”“注意模块边界”，这些也写了。可真要加一个功能，应该用现有的哪套机制，还是现有机制本身就得改，并没有跟着讲清楚。光把原则摆在那里，Agent 还是可能照着眼前能跑的写法继续做。

本质上还是模型的上下文是有限的，并且越长的上下文模型表现得会越蠢，而且很多约束通过文档还是不够强导致。

另一方面，这也不能全怪 Agent。想让它一直干活的是我，希望一觉睡醒就多出一批功能的也是我。项目进展跑偏，很大程度上也暴露我对整体架构把控的问题，本身还有这么多没理顺的地方，我就急着让它自己循环起来。前面写出来的东西又会被后面参考，越跑，离我想要的架构反而越远。

那种心情还挺矛盾的，新东西还是想试，但一打开项目，又得先收拾已经写出来的东西。本来是下班以后找点乐子，搞着搞着，像给自己又找了一份工作。

攀上开悟之坡

到了这里，也没办法继续只盯着加功能了。同样的问题已经来回出现，再交一批任务给 Agent，估计还是得回来收拾。

于是我把大部分的卡牌实现都清空，从头定义实现的路径，具体来说这回我做了几个事情：

  1. 优先把复杂的卡牌先梳理出来，保证架构能支持这些逻辑。然后先实现小范围的几张，并 review 了下整体架构没有跑偏。
  2. 让 Agent 自动整理实现新卡牌的时候对现有架构的冲击，看看是否需要更新进我们的架构文档。
  3. 约定实现卡牌时必须在单卡文件内闭环，如果不能，需要停下来说明原因。
  4. 把架构约束固化成 CI 检查项，每次合入前强制校验。
  5. 测试分层，卡牌实现需要有后端的 session 级别的测试覆盖正向和负向 case。
  6. 多 Agent 交叉 review。

同时这个时候我发现了一个好用的 Matt Skills，相比于 Superpowers，其有如下优势：

  1. grill skill 能帮助我在实现前反复确认所有细节，很多时候可以帮助我发现想法的漏洞或者之前代码实现的问题，达到快速修正的效果，从而保证不会跑偏。
  2. 其和 GitHub 的集成也更好，所有的 issue 都可以跟踪。
  3. 真正的实现阶段效率比 Superpowers 快，而且由于前期 spec 定义清楚，后续实现基本上全托管状态。

这些围绕 Agent 开发本项目而准备的东西，我把它们叫作 项目级别的 Harness。项目资料去哪找，已有代码该怎么用，写错了怎么发现，都在里面。通用的 Skills 可以继续用，但 Open Agricola 自己这些问题，还是得自己整理，装上一个工具并不会自动解决。

折腾到五月底、六月初，项目自己的 Harness 总算理出了一版。发现问题以后，除了改掉眼前这处，也会把能补的检查补上，该留下的说明留下。还谈不上多成熟，至少开始有办法把这些经验留给下一次任务了。

Vibe Coding 降低了实现门槛，但没有降低驾驭复杂系统的难度，对于这个项目而言终于算是走上了正轨，我还想加更多人数和扩展，不过在让 Agent 继续跑之前，得先把这个项目本身彻底理顺。后面能不能撑住，接着做才知道。
